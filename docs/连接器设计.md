| # | 问题 | 决策 | 含义 |
|---|---|---|---|
| **D1** | 连接器形态 | **(a) 边适配器,且对用户不可见** | 连接器是边的内部属性:**没有专用 UI**(无连线 chip、无切换入口、无固化节点)。用户只见「节点的端口有值了」,不见「连接器」这个概念 |
| **D2** | 端口声明权威 | **(a) Provider capabilities 为准** | 端口表由引擎能力派生,单一事实来源;`COMPAT` / `SHOT_REF_ROLES` 退场(前置:补齐 capabilities 的 `ref-audio`) |
| **D3** | 缓存粒度 | **分阶段:先「路径+参数」(S1–S3),S4 升级「内容 hash」** | 先拿正确性与可见性,S4 再解决同名覆盖等边界 |

**D1 的三个直接推论**(影响全篇):

1. **绑定是派生态、不落盘** —— 连接器由 `(源类型, 目标端口)` 唯一确定,绑定可从「边 + 上游产物 + 目标 mode」重新推导,不需要新持久化结构。
2. **参数只有两个去处** —— 要么由端口唯一确定(`first-frame` ← 视频尾帧),要么由**目标节点的 data** 承载(如取帧位置 `at: 'first'|'last'`,放在 image-edit 节点上,现有检查器已实现)。连接器自身没有 UI、不存参数。
3. **失败与状态走既有面** —— 不新增「连接器面板」;诊断信息进**调试面板/日志**,用户级提示走 **toast / 节点角标 / Agent 校验卡**。

## 1. 背景与目标

### 1.1 问题

画布上「上游产物 → 下游参数」的转换逻辑,目前是**隐式、硬编码、分散**的:

| 症状 | 现状 |
|---|---|
| 转换逻辑写死在渲染层 if/else | `CanvasPage.tsx` 统一边分派 effect:`switch (dst.kind)` 手写各类注入 |
| 语义只有字符串 | `CanvasEdge.label` 是自由字符串(`first-frame` / `ref-image` / `slot-<name>`…),无类型、无实现者 |
| 声明重复三处 | `COMPAT`(连通性)、`SHOT_REF_ROLES`(可用角色)、`h3c.capabilities().videoModes[].refs`(Provider 声明)各说各话 |
| 失败静默降级 | 抽帧失败 → 不注入 → 静默走文生,用户不知道「接续没生效」 |
| 无缓存/无失效 | 同一尾帧反复抽;上游重跑后是否刷新靠手写比对(`tailFrameFrom`) |
| 中间产物无归属 | 抽出的帧只是磁盘文件,无键、无状态、无法复用 |

### 1.2 目标

把「把上一个节点的产物,变成下一个节点需要的数据」抽象为**内部机制**(而非用户功能):

- **类型化**:连通性由类型推导,不再手写 `COMPAT`
- **可执行**:转换是主进程里真有实现的函数(抽帧、取音轨、抽文案……)
- **可缓存**:产物按内容寻址,可复用、可失效、可追溯
- **可诊断**:机制对用户不可见,但**结果必须在节点上可见**、**失败必须可定位**
- **可演进**:新增转换 = 注册一个定义,不动节点渲染与图结构

### 1.3 非目标

- ❌ 不做连接器的可视化(边 chip / 面板 / 切换入口)——D1
- ❌ 不做「固化为一等节点」——D1 已排除(如将来需要,作为独立提案)
- ❌ 不做通用可视化编程(DAG 表达式/条件分支/循环)
- ❌ 不改 Provider 与 CLI 构造层(最后一跳保持现状)

## 2. 术语(统一语言)

| 术语 | 定义 | 载体 | 用户可见? |
|---|---|---|---|
| **边 (Edge)** | 拓扑连接:`source → target` | `CanvasEdge` | ✅ 看得见线 |
| **端口 (Port)** | 节点上的输入位/输出位,带类型与基数(shot 的 `first-frame` / `ref-image` / `prompt`) | `PortSpec`(新) | 🟡 仅以「节点上的值」体现 |
| **连接器类型 (ConnectorType)** | 类型化转换的声明:接受什么、产出什么 | `ConnectorDef`(新) | ❌ 不可见 |
| **绑定 (Binding)** | 一条边上的一次转换实例(派生态,不落盘) | `Binding`(新,运行时对象) | ❌ 不可见 |
| **产物 (Artifact)** | 转换的输出物:路径 + 缓存键 | `Artifact`(新) | 🟡 作为节点上的值可见 |

一句话:**边是拓扑,端口是插槽,连接器是内部转换器,绑定是推导出来的接线记录。**

## 4. 形态(已定:边适配器 · 不可见)

```
用户视角:
   [镜头 01] ────────────────→ [镜头 02]
        │                           └─ 检查器「参考绑定」显示:首帧 · 上游镜头尾帧 · 自动

实现视角:
   Edge(shot1 → shot2, portAnchor: 'first-frame')
     └─ Binding(派生)  connector: video.frame(at:'last')
          └─ Artifact(…/frames/shot1_xxx-last-1789….png, key: <hash>)
               └─ 写入 shot2.data.refs[0] = { path, role:'first-frame', auto:true }
```

| 备选形态 | 结论 |
|---|---|
| (b) 一等节点 | ❌ 不采用——图会膨胀、需要端口渲染与布局、用户被迫手动接线 |
| (a)+(b) 固化逃生口 | ❌ 不采用(D1 明确「只是边适配器」);如将来需要,单独立项 |
| 连接器可视化(chip/面板/切换) | ❌ 不做——连接器是内部机制,不是用户功能 |

**收益**:零 UI 成本、零新持久化结构、迁移风险最低。
**代价与缓解**:机制不可见 → 调试成本上升 ⇒ 用**日志/调试面板**补足(§9.3),用**节点回显**保证结果可查(§9.2)。

## 5. 类型系统与端口

### 5.1 IO 类型

```ts
type IOType = 'video' | 'image' | 'audio' | 'text' | 'document' | 'any';
type Cardinality = 'one' | 'many';   // many 需 order: 'ordered' | 'set'
```

### 5.2 端口声明(节点侧)

```ts
interface PortSpec {
  /** 端口名(与下游 data 字段/引擎参数对齐,如 refs[].role、shotNodeIds) */
  name: string;
  direction: 'in' | 'out';
  accepts: IOType[];
  cardinality: Cardinality;
  /** many 时上限(如 ref-image ≤ 9)与是否有序 */
  max?: number;
  order?: 'ordered' | 'set';
  /** 动态端口:仅在某些 mode/条件成立时存在 */
  activeWhen?: { field: string; in: (string | number)[] };
  /** 必填端口(提交前校验) */
  required?: boolean;
}
```

**端口是动态的(用户提出的关键点)**:shot 的输入端口随 `mode` 变化——

| mode | 输入端口 |
|---|---|
| `text2video` | `prompt`(text)、`ref-audio` |
| `first-frame` | `prompt`、`first-frame`(image)、`ref-audio` |
| `last-frame` | `prompt`、`last-frame`(image)、`ref-audio` |
| `first-last` | `prompt`、`first-frame`、`last-frame`、`ref-audio` |
| `ref-image` | `prompt`、`ref-image`(image, ≤9, **有序**)、`ref-audio` |

绑定锚定 `(nodeId, portName)`;mode 改变导致端口消失时,绑定进入 **incompatible** 状态并**显式告警**(现状是从 `refs` 里静默删掉)。

### 5.3 端口的权威来源(已定:D2 = a)

| 方案 | 结论 |
|---|---|
| **A. Provider capabilities 为准** | ✅ **采用**——`capabilities().videoModes[].refs` + 节点 kind 派生;单一事实来源 |
| B. 前端常量表 | ❌ 退场(`SHOT_REF_ROLES`、`COMPAT`) |
| C. 双写 | ❌ 必然漂移 |

> ⚠️ **前置工作**:`h3c.capabilities().videoModes[]` 目前只声明帧/参考图角色,**缺 `ref-audio`**(而 `SHOT_REF_ROLES` 每个模式都含音频)。S2 第一步先补齐 capabilities,否则退场会造成能力丢失。

### 5.4 闭合类型(防 N×M)

按「**转换能力 × 类型匹配**」定义,而不是逐 `(源类型, 目标端口)` 枚举:

| ❌ 反例 | ✅ 正例 |
|---|---|
| `video→shot.first-frame`、`video→image-edit.input`、`video→shot.last-frame`… 各一个 | `video.frame(at)` 一个连接器覆盖所有「要一张图」的端口 |
| `image→shot.first-frame`、`image→image-edit.input`… | `passthrough`(类型不变)覆盖 |

### 5.5 端口锚定:边的 label 语义收敛

`label` 从「连接器类型」改为「**目标端口锚定**」:

| 现状 label | 收敛为 | 目标端口 |
|---|---|---|
| `ref-image` / `ref-audio` | `ref-image` / `ref-audio` | shot.refs[].role |
| `first-frame`(shot→shot,上游尾帧) | `first-frame` | shot.refs[].role(**来源由连接器决定:video.frame@last**) |
| `input-frame`(shot→image-edit) | `input` | image-edit.inputFrameSource |
| `input-image`(asset→image-edit) | `input` | image-edit.inputAssetId |
| `input-brief`(document→下游) | `prompt` | *.prompt |
| `slot-<name>`(**例外**) | `slot-<name>` | 锚定**源槽位名**,连接器按 `accept` 决定落哪个目标端口 |

## 6. 接口草案

### 6.1 定义(shared,双端可见)

```ts
// packages/shared/src/connectors.ts(新)
export interface ConnectorDef {
  id: string;                   // 'video.frame' | 'passthrough' | 'media.clip-ref' …
  label: string;                // 仅用于日志/调试,不做 UI
  from: IOType[];               // 接受的上游类型
  to: IOType;                   // 产出类型
  /** 由端口能唯一确定的默认参数(如 first-frame 端口 → at:'last') */
  defaultParams?: Record<string, unknown>;
  /** true = 代价高,需要排队/进度 */
  costly?: boolean;
  /** 同 (源类型,目标端口) 多候选时的优先级 */
  priority?: number;
}

export interface Artifact {
  path: string;
  /** 缓存键(见 §8.1) */
  key: string;
  createdAt: string;
}

/** 派生态:由 (边 + 上游产物 + 目标 mode) 推导,不落盘 */
export interface Binding {
  edgeId: string;
  src: { node: string; artifactPath: string };
  dst: { node: string; port: string };
  connector: string;
  /** 端口默认参数 ⊕ 目标节点 data 提供的参数(如取帧位置 at) */
  params?: Record<string, unknown>;
  artifact?: Artifact;
  status: 'pending' | 'ready' | 'stale' | 'incompatible' | 'failed';
  error?: string;
}
```

### 6.2 注册表与执行(main 侧)

```ts
// packages/connectors/src/registry.ts(新,纯 node 依赖,与 packages/providers 同形)
export interface ConnectorContext {
  /** 只读白名单根(outputSearchRoots()),所有读写必须落在其下 */
  roots: string[];
  sourcePath: string;
  /** 目标节点 data(承载端口默认参数之外的参数,如取帧位置) */
  dstData?: Record<string, unknown>;
  log?: (msg: string) => void;
}

export interface Connector {
  readonly def: ConnectorDef;
  /** 物化产物;必须幂等(同 key 命中缓存直接返回) */
  resolve(binding: Binding, ctx: ConnectorContext): Promise<Artifact>;
  /** 该连接器能否服务 (源类型 → 目标端口) */
  canServe(src: IOType, dstPort: PortSpec): boolean;
}

export interface ConnectorRegistry {
  list(): ConnectorDef[];
  get(id: string): Connector | undefined;
  /** 类型推导:选连接器(兼容性 + 优先级) */
  pick(src: IOType, dstPort: PortSpec): Connector | undefined;
}
```

**放置位置**:实现放 `packages/connectors`(只依赖 `node:fs` / `node:child_process`,与 Electron 解耦);主进程挂载与生命周期;`frames.ts` 迁入成为第一个 Connector;产物沿用 `outputs/`(受 `outputSearchRoots()` 白名单与 `bba-output://` 只读协议保护)。

## 7. 运行时流程

```
① 建边        端口锚定(label)+ 类型校验(不合格的边在「+」弹窗里就不可选)
② 推导绑定     遍历目标节点入边:srcType × dstPort → registry.pick() → Binding(派生)
③ 准备阶段     运行前逐条 Binding:
                 ready 且 key 未变            → 命中缓存
                 pending / stale / 无产物      → connector.resolve() 物化
                 incompatible                 → 阻断并报错(不静默降级)
④ 写端口        artifact 写进目标节点 data 的对应端口字段
                 (等价于今天的 refs / shotNodeIds / slots / inputFrameSource)
⑤ 组装请求     runNode: ports → RenderRequest.references(params)     [与现状一致]
⑥ 引擎         H3cProvider → buildH3Args(--first-frame …)            [与现状一致]
⑦ 完成后       新产物落地 → 其下游 Binding 标 stale(失效传播)
```

**关键收益**:今天散在 `runNode` 里的「现场抽帧兜底」不再是特例,而是 ③ 的统一行为——**任何连接器产物缺失/过期,都在提交前统一补齐**。

## 8. 缓存与失效

### 8.1 缓存键(已定:D3 = 分阶段)

| 阶段 | key 组成 | 说明 |
|---|---|---|
| **S1–S3(现行)** | `hash(sourcePath + params + connectorId + connectorVersion)` | 简单、够用;等价于今天 `tailFrameFrom` 比对路径的泛化 |
| **S4(升级)** | 把 `sourcePath` 换成**内容标识**(mtime+size 或摘要) | 防「同名覆盖导致用到旧帧」(已踩过一次同类 bug) |

### 8.2 失效传播

| 触发 | 动作 |
|---|---|
| 上游节点重跑出新产物 | 其所有出边 Binding → `stale` |
| 连接器参数改动(含目标节点 data 改动,如取帧位置) | 该 Binding → `stale` |
| 下游 mode 改变导致端口消失 | Binding → `incompatible`(显式告警,**不删除记录**) |
| 连接器实现版本升级 | 该连接器全部 Binding → `stale` |
| 边删除 | Binding 消失(派生态);产物文件保留待 GC |

与现有 `node.stale` / `rerunAffected()` 打通:stale 的 Binding 让目标节点也 stale。

### 8.3 产物回收

`outputs/frames/` 会累积一次性帧。产物按 `key` 命名(天然去重);提供「清理未引用产物」工具(引用 = 任一节点 data 中的字段值)。

## 9. 可见性策略(D1 下的核心设计)

原则:**机制不可见,结果可见,失败可诊断。**

### 9.1 不可见的(❌)

- 连线 chip、连接器切换入口、连接器面板、固化节点
- 连接器 id / 参数 / 产物键,都不出现在常规 UI 文案里

### 9.2 必须可见的(✅ 结果层)

| 展示面 | 内容 | 现状 |
|---|---|---|
| shot 检查器「参考绑定」 | `首帧 · 上游镜头尾帧 · 自动`(可看缩略图) | 已实现,保留 |
| image-edit 检查器「输入帧源」 | 来源节点 + 首帧/尾帧切换(**参数由目标节点承载**) | 已实现,保留 |
| timeline 检查器「入线镜头」 | `shotNodeIds` 列表 | 已实现,保留 |
| workflow-output「产物汇聚」 | `×N 个 source 节点` | 已实现,保留 |
| 节点角标 / toast | 「已继承「镜头 01」尾帧作首帧」等一次性提示 | 已实现,保留 |

### 9.3 可诊断的(🔍 排错层)

| 场景 | 呈现 |
|---|---|
| 连接器选择与物化 | 主进程 `DebugLogger` 记录一行:`[connector] edge=shot1→shot2 port=first-frame pick=video.frame(at=last) cache=miss out=…/frames/….png (412ms)` |
| 物化失败 | 日志 `level=error` + 用户级 toast(「尾帧抽取失败:ffmpeg exit 1」),**不再静默降级** |
| 端口不兼容 | 节点角标黄点 + 检查器内联提示;Agent 校验卡(现有 `continuity` 事件通道)汇总 |
| 提交前校验 | 必填端口缺失 / incompatible → 阻断提交,错误文案定位到「哪个节点缺什么」 |

> **红线**:注入的结果必须在节点上可见(§9.2);失败必须至少能在调试面板定位(§9.3)。二者任一缺失即为 bug。

### 10.2 弹窗承诺 vs 派发实现(诚实性核对)

| 端口 | 弹窗承诺 | 派发/运行期现状 |
|---|---|---|
| `first-frame`(shot ← shot) | 上游尾帧自动取帧 | ✅ 抽帧 + refs + 运行期兜底 |
| `first-frame` + **画面规格**(shot ← shot) | 接续上游：比例与档位继承自上游 | ✅ 新增:整组继承 `aspect/width/height/custom*/tier/steps/layers/reuse`(见 §10.3) |
| `first-frame`(shot ← 图片三类) | 首帧 · 直通 | ✅ 新增:上游 `resultPath` 直通为 refs.path |
| `input`(image-edit/upscale ← shot) | 输入帧 · 首/尾帧可取 | ✅ `inputFrameSource` + 运行期抽帧 |
| `input`(image-edit/upscale ← 图片三类 / asset) | 输入图 · 直通 / 原图编辑 | ✅ 新增:`inputImageFrom` 运行期解析(手填 `inputAssetId` 优先) |
| `prompt`(document → 下游) | 提示词 · 全文注入 | ✅ 新增:`promptFrom`,**自身 prompt 为空时**用文档全文 |
| `clip` / `audio-track` / `sequence`(→ timeline) | 片段/音轨入轨 | ✅ 入 `shotNodeIds`(顺序即语义) |
| `output`(→ wf-output) | 产物汇聚 | ✅ 按 kind 写入 `outputs[].sourceNodeIds` |
| `slot-<名称>`(→ wf-input) | 按槽位类型匹配 | ✅ 按槽位名/accept 写入 `slots[].value` |

> 仍待修(不属本次 UI 范围):弹窗选的档位/比例未写进新节点参数(接续场景已被 §10.3 的继承取代,其他场景仍待修);弹窗 `RES/ETA` 与检查器 `SHOT_SIZES/SHOT_TIER_PRESETS` 两套表数值不一致(默认档 1280×720 vs 1280×704;≈8 分钟 vs ≈15 分钟)。

### 10.3 接续链的画面规格继承(shot → shot)

**规则**:上游 shot → 下游 shot 的接续边,下游**整组继承画面规格**:

| 继承 | 不继承(属内容决策) |
|---|---|
| `aspect`、`width`、`height`、`customWidth`、`customHeight` | `frames`、`seconds`(本镜头时长自己定) |
| `tier` 及其三件套 `steps` / `layers` / `reuse` | `seed`、`prompt` |

**理由**:接续链若两段分辨率/档位不同,画面会跳变,且 h3 的 FL2VA 首帧条件在异尺寸下生成质量不稳;档位三件套与 `tier` 必须同进同退(检查器把 tier 显示为预设,单改 tier 不同步 F/S/L/R 会造成数值与档位标签不一致)。

**用户出口**(避免"改了又被覆盖"):
- 下游检查器手动改**任意**规格项 → 自动写入 `specOverride: true`,此后不再被上游覆盖;提示显示「画面规格:自定义(已脱离上游镜头 X)」+「恢复继承」按钮
- 恢复继承 → 清 `specOverride`,下次派发重新同步上游
- 上游重新生成/改档 → 未 override 的下游自动跟随(`specFrom` 标记保持来源可见)
- 「+」弹窗在源为 shot 时**不再显示比例/档位 chips**(它们必然被继承覆盖),改为显示「接续上游：画面规格继承自「镜头 01」(16:9 · preview档 · 864×480)」

**数据结构**(下游 shot.data 附加字段,派生态不落盘到独立结构):

```ts
specFrom?: { nodeId: string };   // 由派发镜像;无接续边时自动清除
specOverride?: true;             // 用户手动改过规格(检查器写入);清除即恢复继承
```

### 10.4 模式自动切换(首帧 / 首尾帧)

**问题**:下游新节点默认 `mode='text2video'`。即使首帧 ref 已注入(h3c 会带 `--first-frame`),UI 仍显示「文生」——用户看到的是「连了视频却还是文生」。

**规则**:

| 场景 | 行为 |
|---|---|
| 接续边(shot → shot)或静帧直通(图片三类 → shot)接入,且下游 `mode` 仍是默认 `text2video`、用户未手动选过模式 | **自动切 `mode='first-frame'`**,检查器提示「由接续连线自动设为「首帧」· 手动点选任一模式即脱离自动」 |
| 用户在下游手动点过模式 chip(任何模式) | 写 `modeOverride: true`;**永不自动改** |
| 接续边被删除,且模式是自动切换来的 | 收回为 `text2video`(手动选过的模式不动) |
| `mode` 为 `ref-image` / `last-frame` | 不注入首帧(h3 的 `--ref-image` 与 `--first-frame` 互斥) |
| 首帧/首尾帧模式但**首帧取不到**(上游未生成 / 绑定未就绪) | 提交前**阻断**并提示,不退化成文生 |

**数据结构**:`modeOverride?: true`(与 `specOverride` 同构,均为「用户显式选择」标记;清除即恢复自动)。

## 13. 风险与边界

| 风险 | 说明 | 缓解 |
|---|---|---|
| **不可见 → 难调试**(D1 主要代价) | 机制藏在内部,出问题只能看结果 | 调试面板逐次记录连接器选择/命中/耗时(§9.3);结果在节点回显(§9.2) |

| 抽象过早 | 为不存在的需求买单 | 分阶段;S1 纯重构、行为不变、可随时回退 |
