## 1. 要解决的问题

当前「用哪个模型」的判断分散在 **4 个地方**,彼此口径不一致:

| # | 位置 | 现有行为 | 问题 |
|---|---|---|---|
| 1 | `packages/providers/src/mlxgen.ts:256` `DEFAULT_MODEL_BY_KIND` | kind → 硬编码 repoId | 改默认值要改代码、要发版;UI 上改不了 |
| 2 | `ImageGenInspector.tsx:30` `d.model ?? 'AbstractFramework/z-image-turbo-8bit'` | 节点无 model 时兜底 | **与 #1 的 `instruction`/`upscale` 兜底不一致**(检查器是默认文生图模型) |
| 3 | `ModelCombo.tsx:20` `IMAGE_MODELS` | 5 个模型的展示清单 | 与 `mlxgen-models.ts` 的 `KNOWN_MODELS`、`providers` 的 `MODEL_ALIASES` **三份手工同构表** |
| 4 | `vision.ts:59` `resolveVisionEndpoint` | 纯 `env` 回退 | **设置页完全管不到**视觉模型,只能改环境变量 ⚠️ |

**核心诉求**:把这些「默认模型」提升为**用户可见、可改的一等设置**,并让所有缺省路径统一从这一个真源取值。

#### 2.1.0 🔴 `image.multiReference` 被整张表漏掉了(Flux 的独有能力)

**「带参考图生成」在现有实现里是一个真实的能力分支,但它没有对应的能力 key。**

证据:`mlxgen.ts:318-335` —— `image-gen` 节点只要带 `ref-image` 连线,就会走一条**完全不同的命令构造路径**:

```ts
if (refPaths.length > 0) {
  if (!/flux.?2.*klein/i.test(model)) throw new Error('带参考图的生成需要多参考模型(当前 X 是纯文生图)...');
  cmd.push('--i2i-mode', refPaths.length > 1 ? 'multi-reference' : 'edit');
  for (const rp of refPaths) cmd.push('--image', rp);
}
```

**三个要点**:

1. **它是 `image-gen` 节点的第二种工作模式**,不是 `image-edit` —— 同一个 `image-gen` 节点,有没有 `ref-image` 连线,**用哪个模型是两回事**。
2. **当前只有 klein 能跑**(实测 `flux2.multi-reference`,`max_images = None` 即**数量无上限**);2.1 的 `max_images = 10`,且走的是 `edit-reference` 而非 `multi-reference`;**z-image 会直接报错**。
3. **`--i2i-mode` 必须按图片数量显式选**(单图 `edit` / 多图 `multi-reference`)—— 源码注释记录了一次真实事故:选错会让路由器改写链断裂,`--image` 被原样透传,argparse 报 `ambiguous option` → exit 2。

**处置**:新增能力 key

| 能力 key | 名称 | 现有 kind 来源 | 当前硬编码默认 | 可选模型(实测) |
|---|---|---|---|---|
| `image.multiReference` | 多参考生成 | `image-gen` **带 `ref-image` 连线时** | `AbstractFramework/flux.2-klein-9b-8bit`(唯一可用) | klein |

> ⚠️ **这条几乎必然要点名 klein**:它是目前唯一支持无上限多参考的模型。设置页该行应显示「当前仅 Flux.2 Klein 9B 支持」的说明,而不是给一个看似能自由选择的空下拉。

#### 2.1.2 🔴 实测推翻的两个旧假设 + 一处探测陷阱

**陷阱 P(最隐蔽,直接影响本方案的落地方式)** —— **不带 `--base-model` 时能力会被严重误报**

```
mlxgen capabilities --model mlx-community/Qwen-Image-Edit-8bit
  → 只报 2 条:qwen.text / qwen.latent          ← 漏了 edit / inpaint / outpaint / reframe

mlxgen capabilities --model mlx-community/Qwen-Image-Edit-8bit --base-model qwen-image-edit
  → 正确报 6 条:qwen.text / qwen.latent / qwen.edit / qwen.inpaint / qwen.outpaint / qwen.reframe
```

**这就是「矩阵必须走 `BASE_MODEL_HINTS` 同一条路由」的硬证据**:探测时的提示缺失,与生成时缺提示会被家族兜底误路由,是**同一个根因**。所以 §3.3 的矩阵**不能靠离线跑一次填死**,须与 `BASE_MODEL_HINTS` 保持一致,并在单测里锁住。

**旧假设 1 ❌ — 「Qwen Image Edit 无 latent I2I 能力」**

`mlxgen.ts:452` 的注释与守卫都断言 Qwen Image Edit 没有 latent 能力。**实测:它有 `qwen.latent`(`supports_image_strength = true`)。**

> ⚠️ 但**不要急着删这句守卫**:该注释说这是「2026-09 真实跑实测」得出的 —— 可能是「能力声明有、实际跑 exit 2」的差异(声明与实现不一致)。**处置:保留守卫,但把文案从「无 latent I2I 能力」改为反映真实原因**(待实测确认是声明虚标还是真不可用)。这是一条独立待办,不阻塞本方案。

**旧假设 2 ❌ — 「2.1 只在指令编辑模式可用,其余模式拿不到专属参数面」**

实测确认 `qwen21.edit` 只有 `supports_mask = false`、`supports_outpaint = false` —— 所以 **2.1 的参考编辑能力就只是「指令编辑」,不存在「被绑死在单 mode」这回事**。

> ✅ **结论(对应你的决策 2「有就要接」)**:2.1 的 **inpaint / outpaint 能力实测不存在**(引擎没声明 mask / outpaint 支持),因此**无需接线,也不该接线** —— 接了也是 `exit 2`。
> 但 2.1 的 **`qwen21.latent`(图生图)实测存在**,**这一条必须接** —— 而它现在正被缺陷 A 挡在门外。

```ts
/** 工具模型绑定 —— 按能力指定默认模型(缺省 = 该能力的内置兜底,见 DEFAULT_TOOL_MODELS) */
export interface ToolModelBinding {
  /** 生成类能力的模型(repoId / 本地目录路径 / 别名) */
  image?: Partial<Record<ImageCapability, string>>;
  /**
   * 看图反推(vision.caption)的模型来源。
   * 不填 = 回退到现有链路:BIGBOTART_VL_* env → 主 LLM env → 本地默认。
   * 注意:它不是「继承 settings.llm」—— 主 LLM 往往没有视觉能力,
   * 一个静默的继承会把「看图」悄悄指向一个看不懂图的端点。
   */
  vision?: LlmSource;
}

export type ImageCapability =
  | 'image.generate' | 'image.img2img' | 'image.instruction'
  | 'image.inpaint' | 'image.outpaint' | 'image.upscale'
  | 'image.multiReference';   // 🆕 带 ref-image 连线的生成(§2.1.0)

// AppSettings 内新增字段(可空,老 settings.json 无此字段 → 全部走内置兜底)
toolModels?: ToolModelBinding;
```

**为什么 `image` 存字符串、`vision` 存 `LlmSource`**:图片模型就是一个 repoId(或本地目录),而 LLM 有端点 / key / 云端供应商等复合结构 —— 直接复用现有 `LlmSource` 类型。

> 📌 相比初稿,`llm?: Partial<Record<LlmCapability, LlmSource>>` 这个**映射被砍成了单个 `vision?: LlmSource`** —— 因为不再需要 `chat`/`plan`/`compact` 三个 key,而只为一个能力保留一层 `Record` 是过度设计。
